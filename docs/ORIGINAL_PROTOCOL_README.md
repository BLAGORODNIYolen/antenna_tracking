# Drone Telemetry Simulator — техническое задание и протокол обмена v2

> **Тип документа:** ТЗ для реализации настольного эмулятора БПЛА на Python и сопряжённого протокола обмена с ESP32.  
> **Приоритет:** (1) математическая модель и управление полётом; (2) обмен ПК ↔ ESP32; (3) наблюдение и диагностика через GUI.  
> **Статус:** целевая спецификация **v2**, а не описание уже реализованного кода. 

## 1. Цель проекта

Разработать настольную программу на Python, моделирующую положение виртуального дрона в локальном трёхмерном пространстве. Программа должна:

1. Управлять перемещением дрона вручную и по простым траекториям **без моделирования аэродинамики и динамики**.
2. Показывать на условной карте дрон, антенну, траекторию, высоту, скорость и расчётное направление антенны на дрон.
3. Рассчитывать **эталонные азимут и угол места** для наведения антенны.
4. Передавать телеметрию, **включая заранее рассчитанные углы**, на ESP32 по USB-UART или Wi-Fi/UDP.
5. По выбору пользователя включать двусторонний обмен, чтобы получать от ESP32 **углы, заданные приводам**, и **реальные измеренные углы положения антенны** как четыре раздельные величины.
6. Позволять сравнивать эталон, команды приводам и реальные измерения; регистрировать отставание и ошибки сопровождения.

**Обязательное ограничение на канал:** при UART **115200 бод, 8N1** передавать телеметрию ПК → ESP32 со средней частотой **не менее 20 пакетов/с** в режиме установленного соединения. Рекомендуемая частота по умолчанию — **25 Гц**, интервал 40 мс. Для двустороннего обмена также задать 25 Гц для ESP32 → ПК.

## 2. Технологии, структура и границы проекта

- **Язык:** Python 3.11+.
- **GUI:** PySide6 (Qt Widgets), без веб-сервера.
- **Карта:** QGraphicsScene/QGraphicsView; простой вид сверху, без 3D-движка и онлайн-карт.
- **Связь:** `pyserial` (UART), `socket` (UDP).
- **Математика:** стандартный `math`, можно использовать NumPy при необходимости.
- **Платформы:** Windows (приоритет), Linux.
- **Проверка протокола:** отдельные автоматические тесты без GUI и ESP32.

Не требуются: GPS, геодезические координаты, аэродинамика, ветер, батарея, модель тяги, реалистичная физика поворота дрона и загрузка реального рельефа. Эмулятор тестирует геометрию наведения и обмен, а не лётные качества.

Рекомендуемые независимые модули: `simulation` (состояние и время), `autopilot` (траектории), `geometry` (расчёт углов), `protocol` (строгая сериализация/парсинг v2), `transport` (UART/UDP), `ui` (карта и панели), `logging` (CSV), `tests` (юнит- и интеграционные тесты).

## 3. Система координат и углов

Применять **локальную ENU (East, North, Up)** в метрах:

- `X` — восток (вправо на карте);
- `Y` — север (вверх на карте);
- `Z` — высота над условным нулевым уровнем (вверх).

**Положение антенны в MVP зафиксировано в (0, 0, 0).** В следующих версиях может быть добавлено смещение антенны, но тогда потребуется явно согласовать её координаты между ПК и ESP32 либо оставить вычисление геометрии исключительно за ПК.

- **Азимут (AZ)**: градусы по часовой стрелке от севера: север = 0°, восток = 90°, юг = 180°, запад = 270°. Допустимый диапазон `[0, 360)`.
- **Угол места (EL)**: градусы от местного горизонта: вверх — положительное значение, вниз — отрицательное; диапазон `[0, 90]`.
- **Heading** дрона (курс горизонтального движения) **не равен азимуту на дрон**. Heading описывает направление его скорости, AZ — направление от антенны к текущей позиции.
- Все углы в протоколе — **градусы**, **не радианы**. Скорости — м/с, время — миллисекунды, координаты — метры.

Для антенны `(0,0,0)` и дрона `(x,y,z)`:

```text
horizontal_range = sqrt(x*x + y*y)
slant_range      = sqrt(x*x + y*y + z*z)
az_deg           = (degrees(atan2(x, y)) + 360) % 360
el_deg           = degrees(atan2(z, horizontal_range))
```

**Граничные случаи:**

- При `x=0` и `y=0` азимут **не определён**: `az_deg=null`, `az_valid=false`. Если `z≠0`, угол места равен +90° и `el_valid=true`.
- При `x=y=z=0` ни азимут, ни угол места не определены: оба `null`, оба флага `false`.
- **Не заменять неопределённый азимут нулём.** ESP32 должна безопасно игнорировать такую целевую ось или сохранять предыдущую корректную команду.
- Перед передачей выполнять проверку `isfinite`: NaN/Infinity запрещены.

Контрольные положения:

| Дрон (x, y, z), м | AZ, ° | EL, ° |
|---|---:|---:|
| `(0, 100, 0)` | 0 | 0 |
| `(100, 0, 0)` | 90 | 0 |
| `(0, -100, 0)` | 180 | 0 |
| `(-100, 0, 0)` | 270 | 0 |
| `(100, 0, 100)` | 90 | 45 |
| `(0, 0, 100)` | `null` | 90 |

## 4. Модель движения БПЛА

Состояние хранить как числовые величины `x, y, z, vx, vy, vz`, время симуляции, режим полёта и состояние исполнения.

- Полная скорость `speed = sqrt(vx² + vy² + vz²)`.
- Горизонтальная скорость `speed_h = sqrt(vx² + vy²)`.
- Heading при `speed_h > 0`: `(degrees(atan2(vx, vy)) + 360) % 360`. При нулевой горизонтальной скорости — не определён либо сохраняется последний действительный heading **только для GUI**, с соответствующей пометкой.
- Для движения с постоянной скоростью: `p(t+dt)=p(t)+v*dt`.
- Расчётный шаг модели — 20 мс (50 Гц) или чаще, независимо от частоты GUI и передачи.
- Модельное время зависит от множителя скорости, реальная частота передачи — **не зависит**.

### Режимы управления — обязательный минимум

**Ручной:** непосредственное задание `(x,y,z)` (телепортация), управление клавишами W/A/S/D (горизонтальное движение), Q/E (набор/снижение высоты), ввод скорости и курса, остановка.

**Прямая:** задать конечную точку `(x1,y1,z1)` и скорость; движение с постоянной скоростью по направлению к точке; точная остановка при достижении, без перескока.

**Окружность:** пользователь задаёт `(cx,cy)`, радиус `R>0`, высоту `z`, линейную скорость `V≥0`, начальный угол и направление вращения; программа использует:

```text
phi(t)   = phi0 + sign * V/R * t
x(t)     = cx + R*cos(phi(t))
y(t)     = cy + R*sin(phi(t))
z(t)     = z
vx(t)    = -R*omega*sin(phi(t))
vy(t)    =  R*omega*cos(phi(t))
vz(t)    = 0
omega    = sign*V/R
```

Здесь `phi` отсчитывается математически от оси +X против часовой стрелки, `sign=+1` означает вращение против часовой стрелки, `sign=-1` — по часовой стрелке.

**Управление моделью:** Start / Pause / Resume / Stop / Reset, множитель 0.25×, 0.5×, 1×, 2×, 5×. Нельзя блокировать интерфейс интегрированием модели или операциями ввода-вывода.

### Состояния и отправка при паузе

- `RUN`: модельное время и координаты изменяются согласно выбранной траектории.
- `PAUSE`: координаты и `sim_ms` не изменяются, **передаваемые компоненты скорости равны нулю**; внутренние параметры движения сохраняются для продолжения.
- `STOP`: модель остановлена; передаваемые скорости равны нулю, положение сохраняется до Reset.
- Если транспорт **подключён**, пакеты должны продолжать отправляться с установленной частотой **и в RUN, и в PAUSE, и в STOP**. Это даёт ESP32 регулярный признак живой связи. При Disconnect передача прекращается.
- `STOP` приложения — не команда аварийного отключения питания приводов. Отдельную аппаратную безопасную остановку следует предусмотреть в логике контроллера.

## 5. Интерфейс приложения

**Центр — карта:** координатная сетка и масштаб; антенна в начале координат; значок БПЛА; текущая и пройденная траектории; линия антенна → БПЛА; в режиме окружности — центр и радиус. Колесо мыши изменяет масштаб, перетаскивание перемещает карту. Простой условный рельеф допускается, но **не влияет** на перемещение или радиовидимость.

**Справа — управление:** выбор режима, поля координат, скорости, курса, параметров окружности/прямой, кнопки Start/Pause/Resume/Stop/Reset, множитель модельного времени.

**Панель телеметрии:** `x, y, z`, `vx, vy, vz`, `speed`, `speed_h`, модельное время, эталонные AZ/EL, горизонтальная и наклонная дальности.

**Панель связи:** выбор `OFF / UART / UDP`, COM-порт, baudrate (по умолчанию 115200), IP, UDP-порты, частота передачи (по умолчанию 25 Гц), флажок **«Двусторонний обмен»**, Connect/Disconnect, фактическая частота и счётчики ошибок.

**Если двусторонний обмен включён:** показывать отдельно:

1. `Target AZ / EL` — эталон от Python, посланный на ESP32.
2. `Commanded AZ / EL` — углы, которые ESP32 фактически задала приводам **после своих ограничений**.
3. `Actual AZ / EL` — **только измеренные датчиками** текущие углы механизма.
4. Ошибку целевой команды и ошибку фактического сопровождения отдельно по AZ и EL.
5. Статус источника измерений, возраст последнего принятого ответа, `seq`, `source_seq`, количество невалидных/пропущенных пакетов и статус `TRACKING / NO_FEEDBACK / STALE / FAULT`.

На карте и боковой проекции по возможности рисовать три различающихся направления: **эталонное**, **командное** и **измеренное**. При отсутствии измерений скрыть «реальный» луч или показать его неактивным; не рисовать его поверх командного как будто положение подтверждено.

## 6. Протокол информационного обмена v2

### 6.1. Общие правила

- **Версия протокола — 2.** Пакеты v1 не следует интерпретировать как v2: наборы полей изменены.
- Кодировка: **ASCII-совместимый UTF-8**. Имена и значения протокола — латиница ASCII; строк с кириллицей не передавать.
- Представление: **один JSON-объект на одно сообщение**; без пробелов и форматирования (`json.dumps(..., separators=(',', ':'), allow_nan=False)`).
- **UART:** 115200 бод, 8 бит данных, 1 стоп-бит, без чётности, без управления потоком (115200, 8N1). Один JSON-объект на строку, завершающуюся байтом **LF (`0x0A`, `\n`)**. Приёмник может игнорировать один `CR` перед `LF`, но передатчик должен писать только `LF`.
- **UDP:** ровно один JSON-объект в одной UDP-датаграмме, **без терминатора LF**. Фрагментация сообщений на несколько датаграмм запрещена.
- **Ограничение размера:** максимум **384 байта на пакет**, включая `LF` для UART. Обе стороны должны соблюдать лимит. При переполнении входного буфера UART сбросить текущую строку до следующего LF и увеличить счётчик ошибок, затем восстановить синхронизацию.
- Типы JSON: `int`, конечное число `float`, строка, логическое значение, а также `null` только в явно разрешённых полях. Значения `NaN`, `Infinity`, `-Infinity` запрещены.
- Поля `seq`, `sim_ms`, `host_ms`, `mcu_ms`, `source_seq` (когда не `null`) — целые без знака 32 бит, диапазон `0…4294967295`; переполнение обрабатывать циклически. `seq` **независим** в каждом направлении.
- Дробные значения координат, скоростей и углов округлять **до 3 знаков после запятой в транспортном пакете** (внутри модели точность не терять). JSON может опускать конечные нули, например `90` вместо `90.000`.
- Получатель обязан проверять `protocol`, `version`, наличие обязательных полей, типы и допустимость чисел. Неизвестные дополнительные поля v2 можно игнорировать; обязательные поля удалять нельзя.

### 6.2. Пакет ПК → ESP32: `DRONE_SIM`

**Назначение:** текущая позиция виртуального дрона, скорость и **рассчитанные на ПК** целевые углы для наведения.

**Все перечисленные поля обязательны.**

| Поле | JSON-тип | Единица / диапазон | Назначение |
|---|---|---|---|
| `protocol` | string | строго `"DRONE_SIM"` | Тип/имя сообщения |
| `version` | int | строго `2` | Версия протокола |
| `seq` | uint32 | 0…2³²−1 | Номер пакета ПК |
| `sim_ms` | uint32 | мс | Модельное время; на паузе не растёт |
| `host_ms` | uint32 | мс | Реальное монотонное время с начала сеанса приложения; растёт на паузе |
| `mode` | string | `RUN`, `PAUSE`, `STOP` | Режим модели |
| `x` | number | м | Координата дрона на восток |
| `y` | number | м | Координата дрона на север |
| `z` | number | м | Высота относительно антенны в начале координат |
| `vx` | number | м/с | Восточная составляющая скорости |
| `vy` | number | м/с | Северная составляющая скорости |
| `vz` | number | м/с | Вертикальная составляющая скорости |
| `speed` | number | м/с; ≥0 | Полная скорость, `sqrt(vx²+vy²+vz²)` |
| `az_deg` | number/null | [0,360)° | **Предрассчитанный азимут на дрон** |
| `el_deg` | number/null | [−90,+90]° | **Предрассчитанный угол места на дрон** |
| `az_valid` | bool | true/false | Корректность `az_deg` |
| `el_valid` | bool | true/false | Корректность `el_deg` |

**Пример корректного пакета**, дрон `(100,0,100)` м, движется на восток со скоростью 5 м/с:

```json
{"protocol":"DRONE_SIM","version":2,"seq":120,"sim_ms":4800,"host_ms":4811,"mode":"RUN","x":100.0,"y":0.0,"z":100.0,"vx":5.0,"vy":0.0,"vz":0.0,"speed":5.0,"az_deg":90.0,"el_deg":45.0,"az_valid":true,"el_valid":true}
```

Пакет UART заканчивается **ровно одним** `\n`; в UDP отправляется тот же JSON **без** `\n`.

**Пример позиции прямо над антенной:** `x=0`, `y=0`, `z=100`, `az_deg=null`, `az_valid=false`, `el_deg=90`, `el_valid=true`. В этом случае микроконтроллер **не должен пытаться поворачивать азимутальный привод в нулевой угол из-за отсутствующего азимута**.

### 6.3. Пакет ESP32 → ПК: `ANTENNA_STATE`

**Назначение:** сообщить, какие значения ESP32 **задала приводам**, и что **реально измерено** на осях антенны, с привязкой к принятой телеметрии.

**Все перечисленные поля обязательны.**

| Поле | JSON-тип | Единица / диапазон | Назначение |
|---|---|---|---|
| `protocol` | string | строго `"ANTENNA_STATE"` | Тип/имя ответного сообщения |
| `version` | int | строго `2` | Версия протокола |
| `seq` | uint32 | 0…2³²−1 | Собственный номер ответного пакета ESP32 |
| `source_seq` | uint32/null | 0…2³²−1 | Номер последнего **принятого и обработанного** пакета `DRONE_SIM`; `null`, если ещё не было |
| `mcu_ms` | uint32 | мс | Время `millis()` ESP32; не синхронизировано с ПК |
| `cmd_az_deg` | number/null | [0,360)° | Азимут **заданной приводам команды** в общей ENU-конвенции; `null`, если команда не определена |
| `cmd_el_deg` | number/null | [−90,+90]° | Угол места **заданной приводам команды**, с учётом ограничений механики; `null`, если команда не определена |
| `act_az_deg` | number/null | [0,360)° | **Реальный измеренный датчиком** азимут; `null` без действительных данных датчика |
| `act_el_deg` | number/null | [−90,+90]° | **Реальный измеренный датчиком** угол места; `null` без действительных данных датчика |
| `act_az_valid` | bool | true/false | Действительность измерения азимута |
| `act_el_valid` | bool | true/false | Действительность измерения угла места |
| `status` | string | см. ниже | Статус алгоритма и датчиков |

**Допустимые `status`:**

- `TRACKING` — принята актуальная телеметрия; используемые измерения достоверны (для задействованных осей).
- `NO_FEEDBACK` — приводам заданы команды, но нет действительной обратной связи хотя бы по одной оси.
- `STALE` — свежей телеметрии от ПК не было более 250 мс; контроллер должен перейти в безопасное состояние удержания/остановки дальнейшего перемещения.
- `FAULT` — ошибка привода, датчика, парсера или другая неисправность, требующая внимания.

**Пример с датчиками положения:**

```json
{"protocol":"ANTENNA_STATE","version":2,"seq":119,"source_seq":120,"mcu_ms":4817,"cmd_az_deg":90.0,"cmd_el_deg":45.0,"act_az_deg":88.7,"act_el_deg":44.3,"act_az_valid":true,"act_el_valid":true,"status":"TRACKING"}
```

**Пример без энкодера шагового двигателя и без датчика серво:**

```json
{"protocol":"ANTENNA_STATE","version":2,"seq":119,"source_seq":120,"mcu_ms":4817,"cmd_az_deg":90.0,"cmd_el_deg":45.0,"act_az_deg":null,"act_el_deg":null,"act_az_valid":false,"act_el_valid":false,"status":"NO_FEEDBACK"}
```

**Критически важно для прошивки:**

- `cmd_az_deg`, `cmd_el_deg` — **не** автоматически рассчитанные ПК целевые углы. Это значения, которые **ESP32 действительно передала управляющей логике приводов**, с учётом калибровки, механических ограничений и допустимого диапазона.
- `act_az_deg`, `act_el_deg` — **только измеренные значения** от датчиков физического положения. Отправлять «ожидаемый по числу шагов» азимут шаговика или «последний Servo.write()» как `act_*` **запрещено**.
- Если имеется программная оценка угла без датчика, её можно в будущем передавать отдельными **необязательными** полями `est_az_deg`, `est_el_deg`, но `act_*_valid=false` и `act_*=null` должны оставаться неизменными.
- Если отсутствует действительная команда по некоторой оси, `cmd_* = null`. Возвратное значение команды — **не** подтверждение того, что двигатель уже достиг этой позиции.
- Значения в пакетах ESP32 — **глобальные углы ENU**, а не число шагов двигателя, PWM, относительные углы серво или сырые показания датчиков. Их следует преобразовать в прошивке с учётом механического нуля.
- `source_seq` подтверждает **обработку телеметрии**, но не успешное достижение цели приводом.

### 6.4. Требования к порядку, задержкам и состояниям обмена

**ПК (TX):**

1. Модель обновляет состояние независимо от связи.
2. В установленный момент TX (`CLOCK_MONOTONIC`/`time.monotonic()`) ПК формирует **свежий** пакет из текущего состояния с новыми `seq` и `host_ms`.
3. На ПК рассчитываются `az_deg` и `el_deg` по геометрии **до сериализации**.
4. По UART отправляется весь пакет целиком, включая LF. Нельзя считать частично записанные байты успешной отправкой.
5. При перегрузке очереди передачи не накапливать старые координаты: отправлять наиболее свежий пакет; число пропущенных кадров диагностировать. Не смешивать два JSON в одной строке.

**ESP32 (RX и управление):**

1. Неблокирующим способом собирать полные строки UART до LF либо читать UDP-датаграммы.
2. Проверять тип/версию, необходимые поля, допустимость углов и чисел. При ошибке — отклонить **весь** пакет, а не использовать частично обновлённые данные.
3. Проверять порядок `seq` с учётом циклического переполнения; устаревшие или повторные пакеты не должны откатывать текущую цель.
4. Из `az_deg` и `el_deg` получать цели приводов; если `az_valid=false` или `el_valid=false`, не выдавать ошибочные угловые команды по соответствующей оси.
5. При необходимости применять ограничения механики и преобразования «угол ↔ шаги/PWM».
6. Обновлять датчики положения независимо от приёма очередного пакета; без датчиков `act_*` остаются `null`.
7. Передавать `ANTENNA_STATE` с актуальными командными и измеренными углами **25 Гц** при включённом обратном канале; `source_seq` — последнее обработанное значение от ПК.
8. При отсутствии нового корректного пакета **более 250 мс реального времени** переходить в `STALE` и прекращать новые перемещения согласно выбранной стратегии безопасной остановки, сохраняя возможность приёма и восстановления.

**ПК (RX):**

- При выключенном флажке двустороннего обмена продолжать работу и TX, но **не использовать** ответные значения в GUI. Флажок относится к **приёму/отображению на ПК**: в протоколе v2 нет команды удалённого включения/выключения отправки ответов МК. ESP32 может отправлять ответы постоянно при активной связи либо разрешать их локальной настройкой прошивки.
- При включённом режиме валидировать `ANTENNA_STATE`; не подменять отсутствующие `act_*` командными значениями.
- Сопоставлять ответ с отправленной телеметрией по `source_seq`; хранить короткую кольцевую историю отправленных эталонных углов.
- Показывать отдельно «ошибку команды относительно соответствующего `source_seq`» и «ошибку **текущего** фактического сопровождения». Для измерения точных задержек отдельные несинхронизированные часы ПК и ESP32 **нельзя вычитать** друг из друга без синхронизации.
- Если нет обратного пакета более **250 мс**, выводить `RX STALE` и отмечать углы как устаревшие. Старая цифра может оставаться на экране только с явной пометкой о давности.

**Подсчёт угловой ошибки:**

```text
wrap180(a)     = (a + 180) % 360 - 180
error_az_cmd   = wrap180(target_az - cmd_az)
error_el_cmd   = target_el - cmd_el
error_az_actual = wrap180(target_az - act_az)  # только act_az_valid=true
error_el_actual = target_el - act_el          # только act_el_valid=true
```

Поля `target_*` необходимо брать либо из истории по `source_seq` (сопоставленная команда), либо из текущего положения дрона (текущая ошибка сопровождения). GUI обязан подписывать, **какой именно вариант** показан. При недействительном азимуте/угле или измерении соответствующая ошибка — **не определена**, не 0°.

### 6.5. UART: скорость, лимиты и расчёт пропускной способности

Конфигурация интерфейса: **115200 8N1**, full duplex (TX/RX одновременно; один USB-Serial или аппаратный UART). При 8N1 один байт передаётся как 1 стартовый + 8 информационных + 1 стоповый бит, то есть **10 бит на байт**.

**Теоретическая полезная байтовая скорость в одном направлении:**

```text
115200 / 10 = 11520 байт/с
```

**При 20 пакетах/с:**

```text
11520 / 20 = 576 байт/пакет — абсолютный теоретический предел одного направления
```

**При 25 пакетах/с:**

```text
11520 / 25 = 460.8 байт/пакет — абсолютный теоретический предел одного направления
```

Поэтому введён **практический лимит 384 байта** (с LF). Показанные выше конкретные примеры содержат **216 байт** (ПК → ESP32) и **214 байт** (ESP32 → ПК с датчиками), включая LF. На 25 Гц это около **5400** и **5350 байт/с** соответственно — менее половины пропускной способности канала **в каждом направлении**. UART full duplex позволяет передавать эти потоки одновременно; нагрузки двух направлений не нужно складывать как если бы они делили один передающий провод.

**Частота:**

- Настраиваемая частота TX: от 20 до 25 Гц для обязательного профиля UART/115200; повышение частоты — только после автоматической проверки фактической длины пакета и пропускной способности.
- Значение по умолчанию: **25 Гц**. Расчёт модели: ≥50 Гц. GUI: примерно 20–30 кадров/с.
- При нормальной нагрузке и подключении измеренная средняя скорость отправки за 60 с должна быть **≥20 пакетов/с**; приём при двустороннем режиме — также ≥20 валидных пакетов/с в локальном исправном стенде.
- Планировщик I/O не должен использовать задержки GUI-отрисовки как источник тактов передачи. Допускается отдельный worker/thread или асинхронный цикл с монотонными дедлайнами. GUI не должен блокироваться `Serial.write()` или `readline()`.
- Обычные Windows/Linux не дают жёстких гарантий каждого межпакетного интервала в 50 мс. Поэтому **критерий приёмки — измеренная частота за интервал и диагностика джиттера**, а не заявление о real-time-гарантии ОС.
- Для UDP также использовать по умолчанию 25 Гц, частоту можно настраивать независимо в пределах, допускаемых выбранным режимом.

**Требования к UART-парсеру:** входной буфер не меньше 384 байт + 1; неблокирующий разбор; срезание по LF; восстановление после мусора и переполнения; не менее 25 пакетов/с при штатном потоке; отдельные счётчики `rx_valid`, `rx_invalid`, `rx_overflow`.

**Важное правило:** отладочные `Serial.print()` с посторонним текстом **не должны** попадать в UART, по которому передаётся NDJSON. Для логов использовать отдельный интерфейс, выключаемое логирование либо отдельный транспорт. При использовании **отдельного физического UART** (не USB-Serial) соединить TX ПК-адаптера с RX ESP32, RX адаптера с TX ESP32 и общий GND; уровни UART должны быть **3,3 В**, несовместимые 5-вольтовые TTL-сигналы напрямую к GPIO ESP32 не подключать. Не открывать один COM-порт одновременно в Arduino Serial Monitor и Python.

### 6.6. UDP по Wi-Fi

- ПК → ESP32: IP устройства в локальной сети, **порт назначения 5005**.
- ESP32 → ПК: IP компьютера и **локальный порт 5006**.
- Для ПК использовать **один UDP-сокет**, привязанный к `0.0.0.0:5006`, для TX и RX; тогда ESP32 может отвечать на IP/порт **источника** принятой датаграммы.
- ESP32 слушает UDP `5005`, отвечает с локального порта `5005` на IP/порт отправителя последней корректной датаграммы ПК.
- TCP, подтверждение доставки на транспортном уровне, переотправка, шифрование и авторизация **не входят в MVP**. Сеть предполагается доверенной лабораторной; нельзя считать `sendto()` доказательством получения на ESP32.
- Контроль порядка/потерь реализуется через `seq`/`source_seq` и статистику.

### 6.7. Безопасность и обработка неисправностей

- Не слать `NaN`, бесконечности, частично сформированные пакеты, некорректные единицы измерения или неправильную `version`.
- При повреждённой строке или датаграмме — отбросить весь пакет, сохранить предыдущую безопасную команду, увеличить счётчик ошибок.
- При отсутствии правильной телеметрии более 250 мс — `STALE`, прекращение новых перемещений привода / безопасное удержание по правилам стенда.
- На ESP32 для шагового двигателя без датчика положения **нельзя заявлять наличие фактической обратной связи**. Значение положения, вычисленное только из количества поданных шагов, — оценка и должно называться оценкой.
- При использовании сервопривода без датчика положения `Servo.write()`/PWM — **команда**, а не измерение.
- При ограничении механического угла возвращать в `cmd_*` **реально применённую цель**, не исходное требование ПК.
- Предусмотреть тесты на недоступный/отключённый порт, пропажу UDP, разрыв пакета UART, переполнение буфера и восстановление соединения.

## 8. Требования к коду ESP32 (граница ответственности)

В данном проекте **не нужно полностью разрабатывать систему управления двигателями**, но интерфейс прошивки должен быть однозначным:

1. Парсить пакеты `DRONE_SIM` v2 по UART и UDP.
2. Получать координаты, скорости, `az_deg`/`el_deg` и флаги их действительности.
3. Использовать предрассчитанные углы как целевые для блока привода; перерасчёт на ESP32 допускается только как независимая диагностическая проверка, если она включена явно.
4. Преобразовывать целевые глобальные углы в механические команды, учитывать ограничения и калибровку.
5. Публиковать реальные применённые командные углы `cmd_az_deg` и `cmd_el_deg`.
6. Считывать датчики (при наличии) и публиковать `act_az_deg`/`act_el_deg`; иначе передавать `null` и `act_*_valid=false`.
7. Формировать `ANTENNA_STATE` v2 и по UART/UDP возвращать его на ПК.
8. Корректно обрабатывать таймаут связи, ошибочный пакет, переполнение `uint32` и отсутствие датчиков.
9. Не блокировать приём телеметрии во время длительного вращения шагового двигателя или движения сервопривода: планирование шагов/движения должно быть неблокирующим.

**Рекомендуемый цикл МК** (псевдокод):

```text
setup():
    init_uart(115200, 8N1) / init_udp(5005)
    init_actuators_and_optional_sensors()
    last_valid_rx_ms = millis()

loop():
    receive_bytes_or_datagrams_nonblocking()
    for each complete_packet:
        if valid_DRONE_SIM_v2(packet) and seq_is_new(packet.seq):
            last_valid_rx_ms = millis()
            source_seq = packet.seq
            apply_target_angles_with_limits(packet.az_deg, packet.el_deg,
                                            packet.az_valid, packet.el_valid)

    update_stepper_servo_nonblocking()
    read_actual_sensors_if_available()

    if millis() - last_valid_rx_ms > 250 ms:
        status = STALE
        hold_or_stop_motion_safely()

    if two_way_enabled and time_for_next_feedback(25 Hz):
        build_ANTENNA_STATE_v2(source_seq, commanded_angles,
                               actual_measured_angles_or_null, status)
        send_reply_nonblocking()
```

Для конкретного стенда настройки калибровки, ограничений сервопривода и числа шагов на оборот определяются отдельно и **не меняют смысла полей протокола**.

## 9. Тесты и критерии приёмки

Реализовать автоматические unit/integration тесты без ESP32 и стендовые проверки с ESP32.

### Математические тесты

- [ ] Направления N/E/S/W и положение `(100,0,100)` дают ожидаемые AZ/EL из таблицы.
- [ ] При `(0,0,100)` корректно передаются `az_deg=null` и `az_valid=false`.
- [ ] На прямой координаты меняются с заданной скоростью; по достижении точки нет перескока.
- [ ] На окружности при любом `t` расстояние до центра равно `R`, высота постоянна; компоненты скорости согласованы с направлением.
- [ ] Start/Pause/Resume/Stop корректно изменяют модельное время и скорость, но **не отключают** поток телеметрии, пока канал подключён.

### Тесты протокола

- [ ] ПК формирует **все 17 обязательных полей** `DRONE_SIM` v2, включая рассчитанные углы.
- [ ] ESP32/программный эмулятор ESP32 формирует **все 12 обязательных полей** `ANTENNA_STATE` v2, включая четыре отдельных угла.
- [ ] JSON не содержит пробелов форматирования, NaN/Infinity; `version` строго 2, типы и диапазоны проверяются.
- [ ] Одно UART-сообщение завершается LF, одно UDP-сообщение находится в одной датаграмме.
- [ ] Длина сериализованных пакетов в рабочих сценариях **≤384 байт**, превышение выявляется до передачи.
- [ ] `source_seq` сопоставляется с правильным пакетом ПК; независимый `seq` MCU не считается подтверждением пакета ПК.
- [ ] Без датчиков оба `act_*` равны `null`, оба флага `false`; GUI не отображает их как измеренные.
- [ ] При наличии измерений и ограничений привода `cmd_*` и `act_*` могут отличаться; отображаются отдельно.
- [ ] Ошибочный JSON, неизвестная версия, неверные типы, переполнения и повреждённая строка UART не приводят к аварийному завершению.

### Тесты скорости и связи

- [ ] При **UART 115200, 8N1**, в течение **не менее 60 с** при подключении, без внешней перегрузки, ПК передаёт **≥1200 полных пакетов** `DRONE_SIM` (не менее 20 Гц в среднем); целевое количество при 25 Гц — **1500**.
- [ ] В двустороннем режиме на исправном локальном стенде за 60 с ПК принимает **≥1200 валидных** `ANTENNA_STATE` (при ответах ESP32 25 Гц).
- [ ] Измеряемые фактическая частота, интервал между пакетами, число ошибок и пропусков видны в GUI/журнале.
- [ ] GUI остаётся отзывчивым во время длительной передачи и при отключении USB/потере Wi-Fi.
- [ ] При отсутствии новой корректной телеметрии на ESP32 более 250 мс прошивка выставляет `STALE` и выполняет безопасное действие.
- [ ] По UDP локальный программный ESP32-эмулятор обеспечивает round-trip; UART можно проверить через loopback/пару виртуальных COM-портов.
